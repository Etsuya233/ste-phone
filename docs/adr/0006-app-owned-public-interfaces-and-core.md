# App 拥有业务数据与公开接口，Core 提供底层机制

状态：接受，步骤 1–5 已实施；目录、公开接口及实施范围见 [架构文档](../architecture.md)。2026-10-31。

Phone 按 App 模块组织业务与页面，各模块拥有自己的业务数据和公开接口。设置拥有壁纸与模型连接；资料负责外部背景接入及只读 SQL 查询；数据库拥有编辑工作区并消费资料接口；AI 应用拥有自己的 Agent、任务、提示词、工具和业务存储。跨 App 依赖只经过所有者的公开入口，由统一入口显式组装，避免数据来源和修改责任散落在共享服务中。

Core 统一 Pi `streamFn` 传输契约及宿主聊天上下文契约，基础设施实现 ST 请求、协议转换与宿主接线。模型与连接选择、Agent 管理、取消、重试和保存策略由应用决定。页面卸载与业务模块生存分开处理，系统提供生命周期事实，应用处理业务后果；跨聊天操作始终保留明确归属。

该方向补充 0005 的共享 AI 能力范围，保留 0002 的 Memory 视图执行与 0003 的界面会话行为。资料模块对 ST 聊天记录的未来接入拥有责任，但本次不增加聊天 SQL，也不引入通用任务调度、全局服务查找或业务存储框架。其代价是应用需明确声明自身依赖和生命周期策略，收益是所有权与变更范围集中，应用之间可独立演进。
