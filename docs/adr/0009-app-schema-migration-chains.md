# 每个应用独立维护数据版本，Core 执行纯迁移链

状态：接受。2026-11-04。补充 ADR 0006 的数据演进职责。

设置已有 v1—v6 升级分支，微信 v1 下同时存在几代朋友圈媒体结构。各持久数据块使用自己的 `version` 记录 schema 版本，迁移名称用于诊断。Core 提供无存储依赖的迁移执行器，应用维护历史转换与当前结构校验，宿主和预览复用同一应用入口。

迁移步骤明确声明 `from`、`to` 和名称。允许单调版本跳跃，使设置原有 v1—v5 直接收口到 v6，未来再追加 v6 到下一版本；历史步骤固定使用目标版本的字段和默认值。引擎检查版本与路径，在输入副本上执行，负责推进版本，并在结束时调用应用的当前 schema 校验。当前版本仍执行校验，缺失数据由应用创建最新默认值，损坏或未来版本直接报错。

迁移在现有数据读取入口执行，保存沿用所属模块的现有机制。执行器只返回转换后的数据与执行记录，不提供 I/O、全局注册器、就绪状态、持久迁移记录表或跨应用事务。当前应用目录清理和可选字段默认值继续按其读取规则运行，避免把持续协调规则误作只执行一次的迁移。

微信用 v1→v2 收口全部已发布 v1 媒体格式，包括已经使用新媒体数组的 v1；v2 只接受当前数组结构。日记没有需要版本迁移的结构变化，继续保持 v1。该选择保留同步初始化与已有保存时机，未保存的旧聊天下次读取仍会转换；旧版微信构建无法读取 v2 数据。
