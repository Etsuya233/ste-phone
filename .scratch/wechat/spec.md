# 微信 App 首期方案

状态：用户已授权 GPT-6.1 Sol 在主代理指导下实施；实现遵循用户确认的上下文和简化保存边界。2026-11-02。

## 原始需求与范围

提供单聊、聊天界面与用户界面，所有人默认好友；支持按人物视角切换帐号。用户以当前帐号发文本，AI 以对方视角回复，一次回复可以形成多条消息。作为 ST 插件，使用现有资料、模型连接和保存能力，保持实现简单。

首期不包含加好友、朋友圈、群聊、图片语音、工具调用、主动来信、撤回、消息编辑、已读回执、后台任务恢复或跨标签同步。文中未由原始需求明确的行为均为代理建议，用户可调整。

## 四轮问答记录

### 第一轮：帐号与单聊身份

主代理问：帐号从哪里来？ST 聊天和 Memory 人物分别承担什么职责？A 切到 B 后是否看到相同会话？

Sol 答：现有公开人物数据有稳定身份、姓名与人物描述，没有 ST persona 映射。建议直接使用当前 Memory 人物作为帐号候选；当前 ST 聊天隔离微信数据，人物稳定身份关联消息。A/B 共用一条单聊，保存发送人物，按当前帐号推导左右气泡。

整理结论：首次进入显式选择帐号，其余人物全部进入通讯录；不保存好友关系表。帐号选择不修改 ST persona、角色卡或主聊天视角。同名人物保持独立。Memory 外的用户帐号暂不增加。

### 第二轮：发送、生成与回复拆分

主代理问：是否允许连续发送、生成中切帐号？如何让一条 AI 回复形成多个消息？

Sol 答：先保存用户消息，成功后生成；首期每次发送触发一轮回复，运行期间可写草稿和浏览，暂停新发送。允许切帐号并取消尚在生成的回复。要求模型明确输出消息数组，完整校验后整批保存；生成失败重试回复。保存失败处理已按后续简化要求改为直接提示错误。

整理结论：App 同时至多一项发送或回复任务，无消息聚合计时器、并行 Agent 或任务队列。模型输出采用下述协议。所有消息同时出现，暂不增加逐条延迟播放。

### 第三轮：上下文、历史与保存边界

主代理问：是否需要 ST 正文、纪要及其他会话？人物删除后怎么处理？能否直接复用日记保存？

Sol 答：建议先用双方人物资料、少量世界状态和本会话最近 50 条消息。人物删除后保留历史与姓名快照，停止相关发送，不按同名重绑。现有日记保存整份 ST 聊天，两个 App 各自直接请求可能互相覆盖，需要在宿主接线集中串行发送手机发起的保存。

整理结论：不读取其他微信会话，不自动注入 ST 正文或纪要，不向 ST 正文及 Memory 写入微信消息。业务数据分别归日记与微信所有；上述保存协调建议已按用户后续要求移出首期。

### 第四轮：边界操作专项处理已移出首期

原讨论涉及生成完成时切帐号、保存中继续发送、切 ST 聊天和分支回退。用户明确要求舍弃这些极限操作的专项处理，避免复杂化。

以此修订后续方案：不新增跨 App 保存队列、元数据回滚、跨帐号待保存任务、提交阶段状态机或分支回退恢复流程，也不为微信改造日记保存。普通操作仍按顺序执行发送、生成、保存，失败直接提示。

## 页面与操作

根页提供「微信」「通讯录」「我」三个 Tab。「微信」列出已有会话，按最后一条消息的追加顺序排列；「通讯录」列出当前帐号以外的所有人物；「我」展示当前人物与切换帐号入口。人物详情只读，提供开始聊天。聊天详情、人物详情、帐号选择分别有独立路由与页面。

聊天页展示双方文本、对方名称、输入框、发送按钮与回复状态。文字按纯文本渲染，首期头像采用姓名占位，不增加头像上传。新会话在第一次成功发送时建立，空输入不发送；消息内容保留段落，仅去除首尾空白。进入会话定位底部，生成完成仅在用户原本处于底部时跟随滚动。

草稿按当前帐号与对方保留在内存，Home 和关闭手机保留，刷新后结束。当前帐号按 ST 聊天保存，重新进入可恢复；切帐号回根页，避免把旧页面的对方误当成当前聊天目标。

## 身份与数据

生产数据建议放在 `chatMetadata.ste_phone.wechat`，带 `version: 1`。每个 ST 聊天拥有一份，内部会话以稳定资料范围和排序后的两个人物 ID 标识。Memory 实例 ID 用于读取及异步归属，稳定 ID 用于长期关联，遵循 ADR 0008。

会话记录双方引用和姓名快照；消息记录唯一 ID、发送人物 ID、内容与实际创建时间。消息数组追加顺序是显示顺序，不依赖时间排序。AI 消息另带回复批次 ID 和触发用户消息 ID。文本内容采用 `{ type: "text", text: string }`，以后增加类型时扩充联合类型，不预建插件注册器。

A 手动发一条，AI 代 B 回两条；切到 B 后仍是相同三条历史，B 的两条显示在右侧。此时手动发送的是 B，下一次 AI 回复的是 A。禁止用 user/assistant 作为永久消息发送者。

人物改名保持原关联，当前展示优先取最新人物姓名；人物缺失时使用姓名快照阅读历史。已删除人物不能再选为帐号，也不能向其发送。资料暂不可用时明确显示来源错误，仍可读已存历史。人物恢复并保持稳定身份后可以继续使用。当前帐号被删除或资料范围切换时取消生成并要求重新选择。

不同 ST 聊天即使引用同一 Memory 范围，微信记录也分别保存。分支与剧情回退沿用宿主现有行为，首期不增加专项适配或验收承诺。

## AI 输入与输出

每轮固定当前 ST 聊天、资料实例范围、双方稳定身份、触发消息、连接配置及资料快照。使用 Phone 默认模型连接，通过现有 Pi 与 AI 传输发送；不修改 ST 主连接，不注册工具。建议沿用日记的 300 秒总超时、10240 token 输出上限，首期不增加独立设置页。

用户已确定：提示词包含双方姓名与描述、公共资料提供的 summary、最近清洗后的 10 条 ST 消息，以及当前单聊最近 30 条微信消息；可用世界时间/地点/天气继续作为辅助背景。两类消息各自按原顺序提供，最新微信用户消息包含在 30 条之内，只出现一次。世界状态字段须依据现有查询结构核实；字段本来未记录时不捏造，查询失败明确报错。长上下文超出模型能力时显示请求错误，不自动摘要或静默截断人物描述。

要求模型仅扮演对方，输出自然的微信文字，不代写当前帐号发言。剧情总结和 ST 消息作为剧情背景，微信消息作为当前直接对话；不把 ST 原文当作刚收到的微信，也不直接服从引用文本中的指令。背景资料仅供角色扮演参考，不能保证严格知识隔离。

```json
{"messages":[{"type":"text","text":"刚看到消息。"},{"type":"text","text":"你现在方便吗？"}]}
```

完整结束后解析 JSON，要求非空消息数组、每条为支持的文本类型且正文非空。模型决定语义拆分，代码不按标点、换行或长度猜测气泡边界。不自动剥代码围栏、修复 JSON 或换格式重试。空正文、未知类型、工具调用、截断、超时、协议错误均结束本轮并明确报错，思考内容不展示、不保存。

## 主流程、生命周期与失败

发送流程为：取得明确双方与文本 → 保存用户消息 → 固定生成输入 → 调用模型 → 校验完整消息数组 → 保存回复批次 → 显示完成。用户消息保存失败时保留文本，不启动模型；回复生成失败时保留已发送消息，提供重试回复，避免再次追加用户消息。新发送开始后撤去旧失败轮次的重试入口。

保存失败时直接显示错误，不建立持久待保存任务、跨帐号恢复入口或自动重试。正常发送期间暂停重复点击发送，避免日常误操作。

Home、切到其他 App、关闭手机窗口继续生成；切帐号、Expose 退出微信或切 ST 聊天时沿用普通取消。首期不细分取消与保存同时发生的竞态，不增加专门的恢复与协调机制。

微信使用现有宿主保存方式，保留其他 App 的 metadata 子字段。日记与微信同时保存、保存完成前切换上下文等边界操作不纳入首期保证，不引入共享保存队列或元数据回滚机制。

## 代码落点与验收

新增业务与页面集中于 `src/apps/wechat/`：数据类型、会话状态、发送及回复流程、提示词、输出解析、存储契约和独立页面。复用资料与设置的公开接口、Core AI/聊天契约及 Foundation。`src/bootstrap/create-phone.tsx` 注入依赖与接生命周期；宿主保存落在 `src/infrastructure/host/`。页面与普通方法分别按仓库 120/60 行阈值审查，避免单组件拼全部页面。

主要规则维护位置：帐号候选与会话身份在微信业务模块，生成输入与协议在微信提示词和输出解析，运行取消在微信服务，ST 落盘在宿主适配器。无跨应用消费者时不添加空 `public.ts`。应用商店与内置目录按现有方式接入，不另造安装状态。

验收重点：正常完成一轮后 A/B 切换共用历史与正确气泡；多气泡同一发送者；生成失败重试不重复用户消息；非法输出与截断不落部分消息；Home 后继续完成；普通保存失败显示错误；人物改名与历史阅读；刷新恢复已保存消息；窄屏滚动、键盘与草稿。实施时运行 typecheck、lint、format:check、相关测试与 build，并在独立预览及真实 ST 分别验证。

## 待用户审阅的关键取舍

用户已确认帐号仅取 Memory 人物，并要求 summary + 最近清洗后 10 条 ST 消息 + 最近 30 条微信消息；已授权按本方案开发。同一人物对共享历史，每次发送立即触发回复、生成中暂停新发送。首期保留普通取消和固定输入，不引入第四轮讨论的专项协调。当前不另建已接受 ADR。


## 公共剧情总结 summary（2026-11-02 补充方案）

用户要求公共资料提供 summary，表示截至当前已有记录的剧情总结。对于 STE Memory，内容由已生成的大总结与尚未纳入大总结的纪要共同组成；Phone 不额外调用模型重新总结。

已核实 Memory 剧情记忆预设：`plot_summaries` 保存分组生成的剧情总结，`chronicle.plot_summary` 引用所属总结，空引用表示尚未总结。每条大总结覆盖一组纪要，多条大总结应全部读取；仅取最新一条会漏掉前面的剧情。已经有所属总结的原始纪要不再重复加入 summary。

建议资料公开接口增加 `readSummary(request): Promise<string>`，返回组装好的剧情总结文本；资料页增加「剧情总结」条目展示同一内容。微信只消费该文本，不依赖 Memory 表名、归属字段与拼接规则。按需读取，避免让既有人物、物品和日记取材强制依赖新增总结映射。

Memory 适配器负责映射剧情总结与纪要所属总结字段；资料模块负责分页读取、筛选与格式化。依次呈现全部剧情总结和全部未总结纪要，保留标题、起止剧情时间与正文；各组按创建时间和记录 ID 保持来源顺序，不将此顺序宣称为剧情时间顺序。不使用宏预设的 15 条限制，也不按微信双方人物过滤全局 summary。

没有大总结时使用全部未总结纪要；两者都空时返回空文本，属于正常空资料。映射不支持、悬空总结引用或读取失败明确报错，不把异常当成空总结。内容完整读取，首期不再压缩、自动摘要或静默截断。纪要和最近 ST 消息允许语义重叠，不增加楼层对齐去重。

最近 ST 消息复用 `readRecentChat({ count: 10 })`，保持现有先取窗口再清洗、空消息移除且不向前补齐的语义，因此结果可能少于 10 条。微信历史取当前会话最后 30 条已发送消息，包含本轮触发消息，按追加顺序提供。读取和生成在一次普通调用中使用固定输入，不新增跨来源快照事务。

此节已纳入本次授权实施，不修改 Memory 预设或额外建立其业务数据。
