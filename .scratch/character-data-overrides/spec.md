# 资料覆写 · 首期人物

在「资料 → 人物 → 人物详情」编辑当前来源中的人物，修正手机应用使用的姓名和背景，并给人物设置一张通用头像。资料应用保存覆写并对外提供有效人物资料，STE Memory 继续维护原始记录，Fake DBeaver 和剧情地图继续查询来源。

## 编辑与保存

人物详情提供「编辑」入口，保留「复制」和来源信息。可编辑姓名、性格、背景、现状及头像。来源自定义字段仍按原顺序显示，首期只读。人物列表、搜索、详情和复制正文均使用有效值；复制内容为文本，头像单独展示。

编辑页显示各文本字段当前生效的值，并标识哪些字段已有覆写。每个已覆写的文本字段可选「恢复来源」，随表单保存后使用届时的来源值。仅保存明确改动的字段，其余字段维持原有的继承或覆写状态。已保存的覆写持续生效，直到恢复该字段，即使来源后来更新成相同值。姓名去除首尾空白后必填，性格、背景、现状允许显式保存为空。比如把来源非空的现状清空后，手机继续显示为空，点击「恢复来源」并保存才重新采用 Memory 当前的现状。

头像通过 Image Hub 图库选择，保存图片引用。更换或清除头像只修改人物引用，图片仍归图库管理。尚未设置、已清除或图片无法加载时，人物界面显示占位；图库不可用时提示原因，仍可编辑文字和清除旧头像。首期在资料应用提供选图和清除，头像仅用于展示，AI 取材只使用文字资料。

点击「保存」后统一提交本次改动，成功后回到详情。保存期间禁止重复提交；失败时保留草稿，已生效资料继续使用上一次成功保存的值，可重试。主动离开有未保存改动的编辑页时确认舍弃，Home 和关闭手机保留当前草稿。

## 归属与来源变化

覆写归属当前 ST 聊天文件、稳定资料空间和稳定人物。相同人物在两个聊天里可以有不同的覆写。同一聊天刷新或重新加载稳定身份相同的资料实例后，覆写继续生效。ST 分支复制聊天元数据时继承当时的覆写，之后各自保存。仅导入 Memory 资料时，覆写仍归原聊天。

编辑页固定打开时的聊天、资料实例与人物身份。来源在同一实例更新时保留草稿，提交前确认人物仍存在，并只提交这次设置或恢复的字段。切换聊天或资料实例时结束旧编辑页，禁止旧草稿向新范围提交。已发出的保存继续写入原聊天，结果只在原归属范围发布。人物从来源移除时，原覆写保留在聊天元数据里，人物从有效资料移除；同名新人物按自身身份读取，原稳定人物重新出现时可再次使用其覆写。

## 生效范围

| 入口 | 读取规则 |
| --- | --- |
| 资料 App | 列表、搜索、详情与复制读取有效资料，列表和详情展示通用头像。 |
| 微信与朋友圈 | 人物界面展示有效姓名与通用头像。下一轮生成使用有效人物资料，包括直接参与者和关联背景中的第三人。 |
| 日记 | 作者选择与人物书目展示有效姓名及通用头像；新生成按有效资料取材，已保存条目沿用写入时的署名。 |
| Twitter | 批量创建账号的人物候选和新账号初始名称采用有效姓名，后续生成读取有效人物背景。已有账号保有自己的名称。绑定人物的账号在未设置账号头像时继承通用头像；清除账号头像后重新继承。账号自定义头像优先，加载失败显示账号占位。路人和公共账号只使用自己的头像或占位。 |
| Fake DBeaver 与剧情地图 | SQL 和地图助手的源表查询读取来源数据。 |

关系、事件等引用仍通过身份匹配。关联资料中单独展示的人物名称采用有效姓名，来源正文中已经写下的姓名保留原文。已保存的消息、日记、帖子与剧情正文沿用原内容。已经固定取材输入的 AI 任务继续使用该快照，下一轮和显式重新生成使用最新成功保存的覆写。

## 简要实现思路

1. 在资料模块集中读取和合并人物资料。以 [标准视图字段](../../src/infrastructure/ste-memory/standard-view-definitions.ts#L10) 和 [资料正文映射](../../src/infrastructure/ste-memory/map-database.ts#L152) 为基础，让来源适配器提供保留字段身份、标签、顺序及显示值的结构化资料项。按字段合并覆写，再按现有格式生成正文；自定义字段原样参与展示。 [PhoneDataService](../../src/apps/data-source/data-service.ts#L32) 通过 [公开资料接口](../../src/apps/data-source/public.ts#L51) 提供统一的人物列表和指定人物读取。以当前实例记录 ID 查询关系，以稳定人物 ID 读取覆写。保留现有只读 SQL 的来源语义。
2. 在 [资料页面入口](../../src/apps/data-source/ui/data-source-app.tsx#L33) 增加独立人物编辑页，复用 Foundation 导航、表单及图库网格。资料模块拥有带版本号的稀疏覆写数据，宿主适配器把它存入聊天元数据的独立 `ste_phone` 字段，预览注入本地存储。未设置的文本字段缺省，显式清空保存空字符串，恢复来源移除该字段。版本与内容按现有规则校验。生产接线见 [应用组装](../../src/bootstrap/create-phone.tsx#L79) 和 [ST 入口](../../src/frontend/index.ts#L33)。
3. 在宿主层串行提交同一聊天的 Phone 元数据写入。轮到某次提交时，确认目标仍可提交，合并最新元数据并固定请求目标，沿用 ST 原生保存和完整性检查。现有微信、日记、地图、Twitter 的聊天元数据写入一并接入这条提交路径，避免不同应用各自发送旧聊天头导致丢失更新。保存成功后发布人物资料变更，刷新依赖人物资料的缓存与订阅；旧读取不得覆盖新结果，来源 SQL 修订号只随来源变化。
4. 将 [微信人物读取](../../src/apps/wechat/wechat-context.ts#L7)、[关联背景](../../src/apps/data-source/read-related-background.ts#L9)、[日记作者和生成取材](../../src/apps/diary/diary-context.ts#L40)、[Twitter 人物列表](../../src/apps/campus-community/campus-context.ts#L14) 和生成背景接到统一的人物资料读取。在各应用展示入口应用通用头像，账号自定义优先级由 Twitter 管理。生成任务在取材时使用同一份已保存的覆写快照。

## 验收

- 同名的两个人物只修改其中一人，列表、搜索、复制、微信展示及新 AI 取材都匹配正确身份；自定义字段仍按原顺序可见。来源 SQL 和地图仍读源值。
- 在编辑姓名期间从 Memory 更新现状，保存后姓名使用覆写、现状采用最新源值。显式清空现状后继续显示为空；恢复该字段时读取最新源值，其他已覆写字段继续生效。
- 刷新、切换两个共享资料空间的聊天、重载同一稳定空间、复制 ST 分支并分别编辑，验证归属。删除人物或切换资料实例后，旧草稿无法误写，同名新人物不会继承。
- 保存失败后可重试，进行中的 AI 生成继续使用已固定的资料，下一轮使用新资料。资料保存与另一 Phone App 同时提交时，两处元数据都保存成功；请求期间切换聊天时，原提交只更新原聊天。
- 从图库设置、更换、清除头像，检查资料、微信、日记和绑定人物的 Twitter 账号。验证账号自定义优先、清除后恢复继承，图片失效显示占位，图库不可用时仍可编辑文本和清除引用。
