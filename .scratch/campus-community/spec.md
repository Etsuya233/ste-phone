# Twitter 需求文档

日期：2026-11-11。状态：核心功能已实现；应用名称调整为「Twitter」，面向通用剧情社交场景。

## 1. 目标与范围

在 STE Phone 中新增独立 Twitter 应用，采用短帖信息流与图文展示，支持人物拥有主号、小号，剧情人物和路人持续发帖、点赞、评论及互相回复。用户既能手动参与，也能主动调用 AI 生成帖子与互动，体验当前 ST 剧情里的社交生活。

首期包含首页、关注信息流、帖子详情、文字和图文发布、账号主页与管理、账号切换、关注、点赞、评论回复，以及两个 AI 入口：「生成一批帖子」「生成本帖互动」。背景热度允许直接使用数字，不要求创建对应数量的账号和内容。

首期不做通知、消息中心、未读数、红点或系统推送；不做逐帖匿名身份、私信、转发、热榜、搜索、定时活动、自动生成、无限互动接龙或背景评论真实加载。匿名感通过昵称与小号实现。视频不列入首期。

## 2. 确认依据与默认约定

用户已确认：人物可以有多个账号；虚拟用户可以发帖、评论、回复和点赞；AI 可以代替当前操作账号发言；手动指定账号时仅在指定范围内选择，未指定时自动选择；背景点赞和评论使用起始计数，未生成的评论展示「还有 xxx 条评论未加载」；首期取消通知。其余沿用讨论中已接受的社交应用方案。

为便于实施，本文补充以下默认约定：手动发帖使用草稿确认发布，批量 AI 帖子与互动完整生成后直接保存；指定账号表示候选范围，不保证每个指定账号都必须出现；普通帖子首次互动以约 20 条实际评论为默认目标，后续续聊不强制凑满；背景计数由程序按热度档位生成，允许用户手动调整。这些属于实施默认值，不表述为用户逐项指定的硬性要求。

## 3. 人物、账号与操作身份

人物是剧情中的个体，账号是其在社区公开使用的身份。一个人物可以拥有多个账号，每个账号独立保存稳定标识、昵称、头像、简介、发言风格、关注关系及发言历史。主号、小号表达同一人物在不同身份下的表现，不拆成互不相关的两个人物。

人物分为关联 Memory 稳定人物身份的剧情人物，以及社区内部保存的路人。路人只需要简短人设，例如职业、兴趣和说话习惯，无需写入 Memory。新闻、公告等公共内容可使用社区内的媒体或公告账号，由公开简介提供生成依据，无需虚构其对应的自然人。

用户可以切换各剧情人物的账号，也可以管理社区账号；当前操作账号决定手动发帖、评论、点赞和关注使用的身份。切换只改变操作身份，同一社区的历史保持共享。主号与小号分别点赞、关注和发言，不能因为归属同一人物而合并记录。

账号管理支持创建与编辑资料、为人物新增账号，以及停用账号。删除路人或账号按停止后续参与处理，既有内容保留署名与稳定引用，不级联删除讨论。账号公开主页只展示该账号的资料和公开内容，管理页面可以查看人物归属。

管理账号提供「批量创建角色账号」选择页，列出当前 Memory 资料空间的全部人物，默认不选，支持多选、全选与取消全选，底部显示选中人数与「创建 N 个账号」。未选时禁用提交。已有关联该人物的公开账号时标注「已有账号」并禁选，停用公开账号同样计入；只有隐藏归属的小号仍可补建。同名人物显示稳定身份，分别创建原名账号。新账号默认启用且公开归属，头像、简介、发言指导留空，不调用 AI。

提交按最新人物与账号重新核验，只补齐所选人物缺少的公开账号；已移除人物或旧资料范围的请求不能提交。人物尚未加载完成以及生成、保存或待保存期间禁止操作。现有账号资料、昵称、停用状态和互动均保留，当前操作账号保持；首次没有操作账号时选中首个新账号。整批一次保存，失败不更改既有数据并保留选择。刷新恢复已保存账号，重复操作不重复创建；后续人物更名不覆盖既有昵称。

小号归属默认不向其他人物公开。管理者能看到归属不代表角色知道；首期不建立身份揭露或知情关系管理系统，也不让 AI 自动认出小号。生成该账号发言时可使用其所属人物的资料，其他账号的上下文不得直接暴露这层归属。

## 4. 信息流与页面

应用主导航包含「首页」「关注」「我」，发布入口持续可达，不保留空的通知页。「首页」展示当前社区的所有公开帖子，「关注」展示当前账号关注的账号所发内容，「我」展示当前账号主页及账号管理入口。

信息流按发布顺序倒序，评论和点赞不使旧帖自动置顶。帖子展示账号署名、正文、图片、点赞数和评论数；点按进入详情，点账号进入主页。账号主页提供关注与取消关注，账号切换后关注页随身份变化。

详情展示完整帖子、实际评论与回复输入。顶层评论按保存顺序排列，回复归入对应讨论串并标出回复对象；页面只展示两级结构，回复楼内评论仍保留明确目标，避免无限缩进。返回信息流保持阅读位置。

手动发布前编辑草稿，可只写文字、只配图片或图文混合，内容不可全空。图片沿用现有图库、描述和手动生图能力，允许先以图片描述占位；AI 可以起草描述和绘图提示词，实际生图由用户主动触发。首期默认最多 9 张图片，模型读取图片描述，无需传入图片文件。图片文件由图库持有，删除帖子只解除引用。

## 5. 背景热度与实际互动

每条帖子分别保存背景点赞数、背景评论数和实际互动记录。背景计数为非负整数，与实际参与账号及评论记录相互独立。

| 显示内容 | 计算规则 |
| --- | --- |
| 点赞总数 | 背景点赞数 + 当前实际点赞记录数 |
| 评论总数 | 背景评论数 + 当前实际评论及回复记录数 |
| 未加载提示 | 背景评论数大于 0 时展示「还有 xxx 条评论未加载」 |

例如，背景点赞 1,200、背景评论 1,000，实际有 3 个账号点赞和 20 条评论，页面显示 1,203 个赞、1,020 条评论，底部显示「还有 1,000 条评论未加载」。顶层评论和楼内回复各计一条。

未加载提示仅表达背景规模，不是可点击控件，不发起网络请求，也不生成对应账号或评论。后来生成的评论作为新增实际互动追加，背景计数保持原值，不消费所谓未加载库存。刷新、重开和切号不重新随机计算热度。

普通帖子应能呈现约 20 个及以上的赞与约 20 条实际评论的热闹体验；首次生成互动以约 20 条实际评论为目标，可以由较少账号多次回复组成，无需创建 20 个不同人物。公共新闻、公告可具有 1,000+ 的背景赞或评论，实际只保存一小批可阅读和回复的评论。

首期采用普通帖子、公共热门帖两种简单热度档位，为背景数提供默认值，具体数值区间在实施时集中配置；用户可在帖子管理中修改两个背景计数。手动发布不会自动调用 AI 补充评论。约 20 条属于体验目标，不作为模型输出不足时整批失败的精确条数条件。

同一账号对同一帖子最多保存一份有效点赞；重复点赞不重复计数，取消点赞只移除该账号的记录，不改变背景数。首期不需要完整点赞名单。

## 6. 评论、删除与持续讨论

用户可以评论帖子、回复任何实际评论，也可以回复自己的内容。评论须有非空文字，保存成功后清空输入；保存失败保留输入与回复目标。背景评论没有可定位的正文和作者，不能被引用或回复。

实际展示过的评论和路人账号必须保存，刷新后保持一致；再次生成互动继续已有讨论，不重写之前的内容。AI 可以围绕用户新回复接话，也可以让其他人物相互回复。

当前账号可以删除自己发布的帖子和评论，AI 代写内容遵循相同归属。删除帖子同时删除其实际评论和点赞；删除评论后保留已有回复，并注明原评论已删除。删除实际评论使总数减一，不改变背景评论数。首期不编辑已发布正文，账号资料和背景计数可单独编辑。

## 7. AI 生成规则

### 7.1 共同入口规则

两种 AI 动作均提供可选的参与账号选择和「本次要求」。当前操作账号始终可以被选择，也可以在自动模式中被 AI 选中；不得沿用朋友圈排除当前账号的规则。

指定账号时，只允许这些账号成为本批作者或点赞者，不自动加入其他账号或新路人；指定列表是候选范围，允许某些账号本次不发言。未指定时，AI 根据话题、账号风格、人物关系和已有讨论自动选择，也可创建少量路人账号。新路人及其首次内容在同批保存，之后可以再次参与。

每次提交固定账号选择、本次要求、目标帖子及所属聊天范围。普通阅读、刷新、手动发布、点赞或评论不调用模型。生成结果不会再次自动触发生成，一次任务完成即停止。

### 7.2 生成一批帖子

结合当前剧情、已有社区内容、候选账号与本次要求，生成一批新帖，可以包含日常生活、吐槽、图文分享、新闻或公告。为保持入口简单，首期批量默认值可设为 3 条，并集中配置，不增加复杂的数量面板。

模型负责作者、正文及可选图片描述，程序负责背景热度数字。引用剧情事实的新闻、公告需有资料依据，允许创作不改变重大剧情的日常细节；无法确定的信息应保留传闻或猜测语气。

完整生成并校验后整批保存，AI 生成帖子可直接出现在信息流。该动作不自动为每条新帖再发起互动请求，用户按需进入帖子生成互动。生成图片描述不会自动调用生图服务。

### 7.3 生成本帖互动

读取目标帖子、已有评论和必要的回复链，生成本批账号点赞、顶层评论或楼内回复。首次互动默认目标约 20 条实际评论，续聊根据已有讨论自然追加，不强制每次补足或新增 20 条。

新回复可以指向已有评论，也可以指向本批更早的评论；目标必须属于同一帖子。不同账号可以有不同观点，允许玩笑、误解和小范围争论，避免所有评论都重复赞美或只回复楼主。

生成不替换既有内容，不凭空引用未加载的背景评论。点赞写入实际账号记录，重复选择已点赞账号不会增加总数。模型返回非法账号、无效回复目标或不合法内容结构时明确报错，不保存部分结果。

### 7.4 背景与知情边界

沿用 Phone 模型连接与资料读取能力，取材包括人物资料、账号风格、世界状态、剧情总结、相关公开背景、社区帖子和评论，以及必要的清洗后 ST 剧情内容。读取窗口在实施阶段明确并集中维护，不将整个社区历史无限塞入请求。

资料用于理解剧情，不能直接推断每个角色都已知情。生成各账号内容时区分其人物经历、公开可见内容、传闻和猜测；同一人物不同账号的表达可以不同，经历应保持一致。不同账号互相对话时不得因系统掌握小号归属而公开身份。

不读取微信私聊作为社区素材，不向 Memory 或 ST 正文回写帖子、路人、猜测或社区舆论。现实设备时间用于显示保存时刻，不据此推进剧情世界时间。

## 8. 保存范围与任务生命周期

社区数据按当前 ST 聊天和稳定资料空间隔离；账号、路人、帖子、评论、关注、实际点赞及背景计数属于社区应用。切号共享历史，切聊天或资料范围不混用数据。刷新后恢复已保存内容，无需模型在线即可阅读。

以下沿用现有应用习惯作为实施默认：同一社区应用同时最多一项 AI 任务；Home 或关闭手机保留草稿并继续生成，Expose 退出应用、切聊天、切资料实例或切操作账号取消尚未保存的生成。进入保存阶段后提交到原范围，切换页面不将结果写入新范围。

取消、模型失败、输出截断或校验失败不保存半批内容及半批新路人；保存失败显示明确错误，不自动再次生成或重试导致重复内容。手动草稿保留，AI 完整结果保留供显式重试保存，重试不调用模型，沿用原批次身份，防止重复创建内容和路人。保存过程暂停冲突的内容修改。

保存失败的 AI 结果仅在当前应用会话内保留，Home 和关闭手机不丢弃；切操作账号后仍归属原批次，重试不改变作者。若存在未保存结果，尝试从 Expose 退出社区时会回到原页面，处理重试或舍弃后可退出。ST 宿主直接切换聊天或资料范围时，社区保留原批次并提示返回原范围重试或舍弃；刷新不恢复未保存结果。暂不做跨标签同步、冲突合并或刷新后的后台任务恢复。

## 9. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 同一人物建立主号和小号 | 资料、关注、发帖历史和点赞身份独立，公开页面不展示归属关系 |
| 切换操作账号 | 历史保持共享，手动操作署名与关注页随账号变化 |
| AI 手动指定包含当前账号的名单 | 当前账号可发言，名单之外账号不参与，未出现的候选账号不会导致失败 |
| AI 不指定账号 | 自动选择合适账号，可包含当前账号，也可创建并保存路人 |
| 普通帖子首次生成互动 | 可生成约 20 条实际评论，包含楼内回复，全部可以阅读和继续回复 |
| 新闻拥有 1,000 条背景评论与 20 条实际评论 | 显示 1,020 条及「还有 1,000 条评论未加载」，提示不可点击 |
| 再生成 5 条实际评论 | 总数增加 5，原评论不变，未加载数保持 1,000 |
| 同一账号重复点赞及取消点赞 | 重复操作不累计，取消仅减去该账号的一份实际点赞 |
| 刷新或重开 | 帖子、路人、评论和背景数字保持一致，无自动模型请求 |
| 回复已有路人评论后续聊 | AI 可以延续该路人的身份和已有对话，回复目标有效 |
| 删除一条已有回复的评论 | 实际计数减一，后续回复保留并标注原评论已删除 |
| AI 起草图文 | 保存图片描述，实际生图需手动触发 |
| 生成失败、停止或切换聊天 | 不出现半批帖子、评论或孤立新账号，不污染新的聊天范围 |
| 完整生成后保存失败并重试 | 保留完整结果，重试不调用模型、不重复创建内容或路人，保存到原聊天与资料范围 |
| 保存失败后离开当前资料范围 | 提示重试或舍弃，Home 和关闭手机继续保留待保存结果 |
| 有大量背景点赞和评论 | 不创建对应规模的实体，无通知、红点或未读状态 |

## 10. 实施边界与维护位置

本文件是本功能需求入口。账号与小号边界维护在第 3 节，背景计数维护在第 5 节，AI 参与范围与追加规则维护在第 7 节，任务归属与失败行为维护在第 8 节。修改这些规则时同步调整验收场景。

实现前阅读 `docs/ui/frontend-development.md` 与 `docs/ui/frontend-preview.md`，沿用现有公共 UI、导航、模型连接、资料与图库接口。社区账号和业务数据由新应用独立维护，不把微信一人物一账号或排除当前账号的限制带入新应用。具体存储结构、组件划分和生成协议留待实施设计，不在需求阶段增加通用社交引擎。

## Twitter 品牌调整

采用经典蓝白配色、小鸟图标和通用社交文案，生成内容由剧情背景决定，不限定校园。多账号、AI 发帖与互动、背景热度规则保持。内部应用 ID 与存储键继续沿用，以保留已有桌面入口、账号和帖子；不接入外部 Twitter 服务。

## Twitter 信息流与交互优化

首页顶部常驻当前账号，点击进入独立切换页；生成中切换先确认停止，保存阶段禁用切换。信息流采用头像左置、紧凑动作和按图片数量变化的网格，单图放大展示。关注页为空时展示推荐账号，排除当前人物的大小号和没有帖子的账号。

帖子详情把调整热度和删除收进 `···`，生成评论留在评论标题旁。评论按头像左置展示并保存本地发送时间，楼内回复保持两级结构和回复目标。手动评论与 AI 批次保存后定位并标出新内容；AI 批次保存完成后自动回到信息流或帖子详情。发布页使用三列配图网格和单图编辑，返回时确认未保存内容；AI 候选按剧情人物、路人和公共账号分组并支持搜索。

评论时间使用可选字段，旧数据缺少时按无时间读取；一次性定位信息只存在内存，不写入持久数据。现有账号、帖子、背景热度、AI 取材边界和存储范围不变。
