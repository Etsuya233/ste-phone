# 微信朋友圈需求文档

日期：2026-11-03。状态：用户已确认；三阶段实现完成，包含 AI 发布动态与 AI 生成互动；保持简单，不增加复杂的一致性处理。

## 1. 目标与需求来源

在现有微信内增加简单朋友圈，让人物发布生活分享、阅读动态，并通过文字评论互相回复。用户明确要求支持文本、图片、视频；图片与视频目前通过描述文本占位；插件运行在 SillyTavern 内，无需严格一致性。

帐号归属、页面组织、数量限制、删除规则及 AI 动作由本次代理讨论提出，用户已整体确认，并明确要求同时实现两种 AI 动作。

基本体验是：选择微信帐号 → 进入发现中的朋友圈 → 发布文字或媒体描述 → 人物发表评论、回复已有评论。手动操作只保存内容；用户主动点击 AI 动作时才调用模型。

## 2. 首期范围

包含信息流、独立发布页、动态详情、文字评论与定向回复、删除自己的内容，以及显式的「AI 发布动态」「AI 生成互动」。沿用当前微信帐号和 Memory 人物资料，不额外建立现实用户、好友或关注体系。

首期不包含点赞、通知与未读、个人相册、搜索、置顶、可见范围设置、共同好友过滤、编辑已发布内容、真实媒体上传/外链/播放/生图，以及定时发布、自动互动或无限接龙。朋友圈与微信单聊各自保留历史，首期不互相注入模型上下文。

## 3. 身份、可见范围与历史

同一 ST 聊天、同一稳定资料空间拥有一份共享朋友圈。当前有效人物都可以成为微信帐号；切换帐号改变发布、评论和删除身份，同一范围的历史保持共享。不同 ST 聊天分别保存，即使它们引用同一资料空间也不合并；切换资料空间不混显，切回可继续阅读原空间历史。

人物引用沿用稳定空间与稳定人物身份，姓名仅用于展示。当前资料中的姓名优先展示；人物删除后保留历史姓名快照，不能以该人物继续操作，不能按同名人物重新绑定。历史内容仍在信息流中可见。资料暂不可用时保留已保存内容的阅读，依赖当前人物的新增操作明确报错。

切换帐号回微信根页，沿用现有导航行为。Home 和关闭手机保留当前页面、滚动位置及内存草稿；刷新后恢复已保存内容，未保存草稿结束。

## 4. 动态内容

每条动态包含可选正文，以及一种可选媒体：1—9 张图片描述，或 1 条视频描述。允许纯文字、文字配媒体、仅媒体；正文与媒体全部为空时不能发布。图片与视频不能出现在同一条动态中。每个媒体描述均须非空，文字去除首尾空白并保留内部段落；首期不增加正文与描述的额外字数限制。

图片按数量排成网格，每格显示图片类型标识和描述文字；单图可使用更宽的占位区域。视频显示单个视频类型占位区域和描述。长描述须可完整阅读，可在详情展开。无上传按钮、外链输入、播放器或可点击的虚假播放控件。描述作为纯文本保存和渲染，不解析 HTML、Markdown 或表情包标记。

信息流按动态保存追加顺序倒序，时间相同时也保持明确顺序。评论不会让旧动态置顶。每条动态显示作者、正文、媒体占位、设备本地时区的发布时间、最近 3 条评论及查看全部入口。设备现实时间用于显示与交流间隔，不能据此推进剧情世界时间。

## 5. 评论、回复与删除

评论只支持非空文字，沿用正文的空白与纯文本规则。点击动态的评论动作，输入直接面向动态的评论；点击某条评论后，输入框明确显示「回复某人」及取消回复操作。提交成功后清空当前输入和回复目标。

评论在动态详情中按保存追加顺序平铺，定向回复显示「A 回复 B」。每条回复指向同一动态下的一条已有评论；不形成多层嵌套页面。用户可以回复自己或他人的评论，动态作者也可继续参与。

当前帐号只能删除以自己身份发布的动态或评论，AI 代写的内容适用同一规则。删除前简短确认。删动态同时删除其所有评论；删评论只移除该评论，其他人的回复保留，并显示「回复某人（原评论已删除）」。为此回复同时保存目标评论 ID 与目标人物引用、历史姓名，避免依赖已删除正文。原评论正文不另存副本，不建空评论占位记录。

首期不编辑已发布内容。正文或媒体描述有误时，可删除后重新发布。

## 6. 页面与交互

微信底栏增加「发现」，其中提供「朋友圈」入口；保留「微信」「通讯录」「我」。朋友圈信息流右上角提供发布入口，另有明确的「AI 发布动态」动作，不能将普通刷新与 AI 调用绑定。当前资料空间已知时，无帐号或人物来源不可用也须保留朋友圈历史入口，新增操作禁用并说明原因；不能沿用现有根页无帐号时整体遮住内容的展示方式。首次进入且没有任何历史范围时，显示选择帐号或连接资料的引导；来源断开后可继续读最后已载入范围，刷新后仍无法识别范围时，提供已保存范围的只读选择，仅用稳定空间标识区分，不猜测它与当前来源的关系。

发布页使用当前帐号，编辑正文，选择纯文字、图片或视频。图片逐项输入描述，支持增加、删除和用上移/下移调整顺序；视频只输入一条描述。切换媒体类型且会丢失描述时先确认。发布成功返回信息流并展示新动态；保存失败保留编辑内容。未保存返回可继续编辑或舍弃。

点击动态进入独立详情页，完整展示正文、全部媒体描述及评论，并提供评论输入和「AI 生成互动」。点作者头像或姓名可进入已有的人物资料页；人物已删除时只显示历史署名，不提供失效资料入口。返回信息流保留阅读位置，不因新评论强制跳到顶部。

空朋友圈说明暂无动态并保留发布入口；空评论区允许直接评论。生成、保存、错误及重试状态在手机内明确呈现。遵循现有 Foundation、NavigationStack 与 Shadow DOM 规则，320px 和 390px 窄屏下正文、长描述、回复目标与操作按钮均可达。

## 7. AI 动作与取材

### 7.1 AI 发布动态

点击后先选择一名当前有效人物，界面明确说明会以该人物身份直接发布。允许用户显式选择当前帐号或其他人物；每次仅生成该人物的一条动态，完整校验后保存。不先建空动态，不保存流式半成品，不额外增加预览确认步骤。

输入包括该人物完整资料、其已保存的回复指导、世界状态、全部剧情总结 summary、该人物的一跳关联背景、最近清洗后的 10 条 ST 消息，以及该人物最近 10 条朋友圈动态。历史范围固定在当前 ST 聊天与稳定资料空间。条数表示读取窗口，清洗后的 ST 内容可能不足 10 条。

### 7.2 AI 生成互动

固定一条目标动态，AI 从当前有效人物中排除当前操作帐号，选择人物生成 0—5 条文字评论或定向回复。动态作者只要未被上述规则排除，也可跟进。排除当前帐号旨在让用户保留自己当前身份的发言权；显式选择人物发布动态具有不同的操作语义。

输入包含候选人物及当前帐号的完整人物资料、按人物身份分开的回复指导、世界状态、summary、最近清洗后的 10 条 ST 消息、目标动态完整内容与媒体描述，以及该动态最近 50 条评论。窗口中评论引用了窗口外仍存在的评论时，只补入其直接目标，不递归追链；已删除目标只提供保留的目标署名和删除事实。

互动首期不额外查询所有候选人物的一跳关联背景。候选名单为空时禁用此动作并解释原因。允许模型返回 0 条，界面提示本次无人回应，维持原动态；用户可再次显式生成。新评论可以回复本轮提供的已有评论，或本批次前面已生成的评论，不能引用未来项、形成循环或指向其他动态。

### 7.3 生成约束

复用 Phone 默认模型连接与现有 Pi 传输，缺少连接时明确提示。建议沿用现有微信 300 秒总超时与 10240 token 输出上限，不新增独立 AI 设置。一次动作一次模型调用，不注册工具，不自动补问或重试格式。

回复指导在朋友圈内扩展为该人物公开表达时的指导；多人互动按人物分别标注，仅适用于对应人物。模型尽力遵循人物性格、剧情事实、秘密与知情范围，不建立角色知识库或事实核验流程，不保证严格剧情一致性。媒体描述作为文本材料，无需视觉模型。

动态与互动使用各自明确的 JSON 输出协议，实施时固定字段和本批引用方式。人物稳定 ID 必须来自本轮允许名单；动态满足第 4 节，评论满足第 5 节与 0—5 条上限。记录 ID 和现实保存时间由插件生成。允许空互动数组；空动态、未知类型、非法人物、非法引用、工具调用、截断或非法 JSON 均明确失败，不保存部分结果、不自动修复 JSON。思考内容不作为正文展示或保存。

不读取微信私聊，不向 ST 正文或 Memory 回写，不把朋友圈自动加入单聊取材，也不沿用单聊记忆屏障或历史条数设置。人物资料、summary、长正文和候选人数不暗中截短；请求过大时直接暴露模型错误，不增加额外压缩调用。这意味着人物较多时会有较大的请求与成本。

## 8. 保存、任务与一致性边界

以普通单页面操作顺序为设计目标：提交输入 → 保存 → 发布界面结果；AI 为固定输入 → 生成 → 完整校验 → 保存 → 展示。手动发布与评论不调用模型；加载、普通刷新、切帐号不调用模型。失败不显示成功。手动保存失败保留编辑草稿；AI 保存失败直接显示错误，本次结果不建立待保存任务，用户可以显式重新生成。重新生成会重新调用模型，界面不能称为「重新保存」。

微信内同时最多一个 AI 任务，单聊与朋友圈互斥。生成期间允许浏览和编辑草稿，暂禁朋友圈提交、删除与其他 AI 动作；普通保存期间也不启动 AI。一次互动完整校验后整批保存，0 条为正常完成，仅显示无人回应。停止、生成失败与输出校验失败均不改变已有内容。用户主动再次生成可能得到重复语义内容，首期不做语义去重。

Home、切其他 App、关闭手机与普通页返回继续生成。切帐号、切 ST 聊天、资料实例更换或 Expose 退出微信取消旧任务，即使稳定空间相同也不能让旧实例结果进入新任务。任务固定发起时聊天、资料实例、稳定范围、人物名单和目标动态。保存阶段的停止沿用现有存储取消能力，等待保存或撤回结束后再恢复操作，明确显示正在保存/停止；不新增朋友圈专用撤回事务。

草稿按当前帐号与目标区分，详情回复目标随草稿保留。未保存返回可继续编辑或舍弃，帐号切换前若有脏草稿可确认舍弃；ST 外部聊天切换不阻拦宿主，清理旧归属草稿。Expose 退出与刷新结束内存草稿，Home 和关闭手机保留。每条手动内容在保存提交时生成设备时间，AI 批次在保存提交时统一赋予时间，批内以追加顺序排序。

本需求不要求跨标签同步、冲突合并、分布式锁、后台任务恢复、自动重试或业务补偿事务；保留现有微信和宿主适配器已经提供的保存行为，不借此改造整个插件。不对多标签并发编辑、跨应用并发保存或宿主文件被外部改写提供额外一致性承诺。

数据由微信模块拥有，保存在当前聊天元数据中，建议扩展现有 wechat 数据，以稳定空间分组保存动态与评论。旧 v1 数据缺少朋友圈字段时按空集合显式兼容；非法数据明确报错。更新时保留单聊、回复指导、帐号与其他应用元数据，不从页面提交陈旧的整份微信快照。

动态记录至少包含 ID、作者稳定引用及姓名快照、正文、媒体类型与描述、现实创建时间、评论集合；评论记录至少包含 ID、作者引用及姓名快照、正文、现实创建时间，以及可选回复目标。AI 来源与批次可作为诊断信息，不改变内容归属。数组追加顺序为权威顺序，历史数量不额外持久化。

## 9. 实施维护位置

现有入口为 `src/apps/wechat/ui/wechat-home.tsx:229` 的 Tab 与 `src/apps/wechat/ui/wechat-app.tsx:15` 的路由。新增发现、信息流、发布、详情各自独立页面，避免继续在根页内拼装完整功能页面。

朋友圈数据类型、规则、操作服务、取材、提示词与解析集中于 `src/apps/wechat/`，按实际职责拆分朋友圈文件。字段及评论引用规则维护在朋友圈领域代码；历史窗口与角色候选维护在朋友圈取材；人物指导和输出协议维护在朋友圈提示词/解析；任务归属和取消维护在朋友圈任务代码。

现有 `src/apps/wechat/wechat-context.ts:29` 是双人单聊取材，朋友圈应独立组织输入，复用资料公开接口。`src/apps/wechat/wechat-generation.ts:10` 提供现有模型调用模式作为参考。`src/apps/wechat/wechat-writes.ts:5` 与 `src/infrastructure/host/wechat-storage.ts:14` 是现有写入与宿主落盘入口，优先复用其真实保存能力。这里只标注已存在入口，尚未创建生产实现。

不新增通用社交框架、权限框架或任务调度器。实施时遵循仓库函数、组件与文件的可读性审查要求，必要注释说明身份、媒体限制、回复目标删除和异步任务归属。

## 10. 验收标准

| 场景                                                    | 预期                                                    |
| ------------------------------------------------------- | ------------------------------------------------------- |
| 发布纯文字、1/9 张图片描述、视频描述                    | 正确保存与展示，刷新可恢复；仅媒体也可发布              |
| 全空、空媒体描述、超过 9 图、混合图片视频               | 不能提交，原因明确                                      |
| A 发布，切 B 评论，A 回复 B                             | 同一动态共享，署名正确，评论平铺且引用正确              |
| 评论回复另一条回复                                      | 显示具体回复人物，不产生多层页面                        |
| 删除有回复的评论                                        | 原评论移除，回复正文保留，原目标显示已删除              |
| 删除动态、删除他人内容                                  | 自己动态确认后连评论删除；他人内容无删除操作            |
| 切帐号、ST 聊天或资料空间                               | 操作身份正确，跨归属内容不混显，切回可读历史            |
| 同名、改名、人物删除、资料不可用                        | 身份不按姓名串联；保留历史署名与阅读，失效操作报错      |
| AI 发布与互动                                           | 每次显式调用；一条动态或 0—5 评论；互动不代写当前帐号   |
| AI 窗口外引用、批内回复                                 | 一跳补充正确，只引用输入目标或本批前序项                |
| 模型失败、非法输出、截断、保存失败                      | 无半条或半批；错误可见，手动草稿保留，AI 可显式重新生成 |
| Home、关闭手机、返回、切帐号/聊天/资料实例、Expose 退出 | 继续或取消符合第 8 节，迟到结果不进入新归属             |
| 手动发布、阅读刷新、打开朋友圈                          | 不请求模型，不改变 ST 正文、Memory 与单聊历史           |
| 旧微信数据首次打开                                      | 朋友圈为空，已有单聊、帐号和指导完整保留                |
| 窄屏、长描述、长评论、返回与未保存离开                  | 输入与操作可达，详情完整可读，滚动和草稿行为明确        |

实施后运行相关测试、typecheck、lint、format:check 与 build；独立预览注入成功、空互动、慢响应、非法输出和保存失败样例，并验证真实 ST 的元数据保存及刷新读取。实现与验收记录见本文第 12 节。

## 11. Grill with Docs 问答记录

以下回答由主代理作为方案提出者回答，Astra Medium 负责质询；用户随后确认按本文实施。

1. Astra 问身份与可见范围。主代理答：按 ST 聊天与稳定资料空间共享，全员可见，切帐号只改操作身份；删除人物保留历史，不按同名绑定。
2. Astra 问 AI 触发粒度。主代理答：建议提供两种显式动作，AI 发布先选人物，互动排除当前帐号；手动操作不自动生成，每次互动最多 5 条且可无人回应。
3. Astra 问内容与评论结构。主代理答：正文配 1—9 图或单视频描述，允许仅媒体；评论只用文字，平铺显示明确回复目标，不做嵌套树。
4. Astra 问删除后引用。主代理答：删除自己的内容；删动态连评论，删评论保留别人回复及原目标署名。信息流、发布和详情独立页面，不做点赞与个人相册。
