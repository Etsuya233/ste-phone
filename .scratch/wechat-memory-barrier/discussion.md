# 主代理与 Sol 6.1 的质询记录

2026-11-03。使用用户指定的 grill-with-docs，结合 grilling 和 domain-modeling。用户明确要求两位代理自行一问一答，不再向用户提问，因此最终规则为代理形成的设计约定。

以下五轮保留最初讨论过程，其中读取旧侧、最早屏障及待回复越界例外均已作废。现行规则以文末方向修订和需求文档为准。

## 第一问：屏障后的新消息怎么回复？

Sol 6.1 问：严格采用 A、B、屏障、C、D 的前缀限制，用户在屏障后发 E，AI如何回复？把 E排除却清除待回复状态会丢任务，直接回复E又与“只读A/B”存在冲突。

主代理答：区分历史与本轮输入。屏障限制历史，当前待回复集合完整作为本轮输入，E能够被回复。回复完成后E才按历史规则排除。界面与文档明确这个例外。

Sol 6.1 复核：可闭合；当前时间上下文直接读取完整消息，会泄漏隐藏消息的时刻与间隔，必须一起改为读取允许序列。

## 第二问：多个开启屏障如何组合？

Sol 6.1 问：A、屏障1、B、屏障2、C，两道开启时取最早边界还是最近边界？关闭其中一道后呢？

主代理答：采用限制交集，最早开启边界生效；两道开启只读A，关闭1读A/B，关闭2仍只读A，全部关闭恢复普通窗口。后面的屏障保留自身开关，生效状态通过顺序推导。

## 第三问：屏障位置怎样稳定？

Sol 6.1 问：绑定消息ID还是可移动数字索引？首条前和空会话要怎样表达？

主代理答：使用 `afterMessageId: string | null` 固定边界，null表示首条前。支持任意消息间、末尾及空会话，新消息永远追加在既有末尾屏障后。空历史仍允许基于本轮输入与背景生成。同位置不重复，首期移动通过删除后重新插入完成。

补充结论：屏障独立存储，归属双人共享单聊；当前发言人物的固定待回复集合为P，其他消息都按历史过滤，不按角色或reply标记重新推测。

## 第四问：生成过程中开关立即生效吗？

Sol 6.1 问：是否立即取消生成再修改屏障？保存阶段还要等待撤回，如何避免旧快照覆盖屏障？

主代理答：采用显式互斥。发送、生成、回复保存、停止撤回期间禁止屏障变更；用户可先用现有停止按钮，完成后再修改。屏障保存期间禁止发送、队列、切帐号及其他屏障写入。变更保存成功后作用于下一次生成，不自动触发回复。

Sol 6.1 复核：方案成立。切ST聊天时原保存锁应持续到旧目标操作完成，旧结果与错误不能覆盖新聊天状态。

## 第五问：旧数据和异常边界怎么处理？

Sol 6.1 问：能否沿用v1可选屏障字段？旧会话、分支继承、锚点损坏与迟到结果如何处理？

主代理答：沿用v1，字段缺失表示没有屏障，首次修改写入。ST复制元数据时自然继承。无效锚点、重复ID或边界、非法字段明确报错，受影响单聊可读但停止生成与屏障编辑。旧目标保存固定归属代次，迟到结果不能覆盖新载入。先构造屏障前消息与P的有序并集，再在允许序列上执行既有窗口规则。

Sol 6.1 复核：质询边界闭合。P必须按消息ID去重并保持原顺序；所有时间从允许序列计算。加入“待回复A、对方B、屏障、待回复C、对方D”验收，确认A/C保留，D不会因pending跨度被带回。

## 文档复核

Sol 6.1 完成文档复核，指出当前会话列表没有空会话处理、部分入口行号不准确。已明确零消息会话暂不进入列表、从通讯录管理，将列表与首次发送失败回滚纳入改动范围，并校正源码入口行号；其余核心规则通过复核。

## 用户方向修订（现行结论）

用户明确：“应该是能读取到屏障之后的内容，也就是更新的内容。”因此采用消息后缀，A、B、屏障、C、D中只读C/D；多个开启屏障采用最新边界，关闭它后退回更早的开启边界。首条前屏障允许全部消息，末尾屏障隔离现有全部消息。

原先允许全部待回复消息越界的例外取消。原队列Q按屏障筛选得到本轮输入P，仅P发送给AI；成功生成后原批次结束，旧侧消息作为用户选择跳过的队列保留在聊天中，关闭屏障不自动重发。失败、停止仍保留Q。时间字段同样只取消息后缀。实施须记录队列已处理截止位置，防止主动开口成功后旧队列通过历史推断再次出现。

Sol 6.1 复核修订：当前删除显式待回复边界后会依据旧触发消息回推，全部旧队列被阻隔时可能再次出现；实现文档已补充独立的队列处理截止位置，真实回复触发消息仅关联实际输入。

## 用户补充：历史条数可配置

用户要求将固定最近30条改为微信设置中的可配置项，默认100，与记忆屏障同批处理；随后明确“先更新文档，先别动代码”。本轮仅修订需求与实现设计。

配置入口确定为“微信 → 我 → 设置 → AI历史消息条数”，按全局微信偏好跨帐号和聊天保存。先截取屏障后消息，再按N取最近窗口，获准本轮输入P完整保留，禁止为补足N回填屏障前消息。每轮固定N，保存新值只作用于后续请求，现有用户升级后也使用默认100。补充正整数校验、保存与草稿行为以及设置v6迁移计划。上述保存范围与交互细节为代理补充约定。

## 实施期间的保存接缝修订

Sol指出旧代次保存完成时若直接丢弃回调，切回同ID聊天后已提前读取的旧状态可能被下次保存覆盖。主代理认可在锁释放前重新读取确认落库的权威数据，保留当前帐号和草稿；旧捕获快照不直接发布。宿主适配器同时处理重新载入的metadata对象，以最新确认写入序号保护微信字段同步，并保留其他插件字段。增加服务及真实适配器回归覆盖这个接缝。
